Rocketry Avionics Flight Electronics Project

Project Summary

Custom avionics for amateur rocketry: RP2350-based flight computers with sensing, navigation, data logging, fin-tab control, LoRa telemetry and pyrotechnic ignition, plus the simulation and analysis tools to tune them from real flight data.

Project Details

  • Two flight computers: the Rice ECLIPSE AFS board and my own M.I.A. (Mission Independent Avionics).
  • RP2350B microcontroller with 16 MB QSPI flash and microSD logging.
  • Sensors: 6-axis IMU, ±64 g accelerometer, magnetometer, barometer, temperature and power monitoring.
  • FreeRTOS on both cores: navigation on core 0, SD logging on core 1.
  • 15-state error-state EKF fusing IMU, barometer and magnetometer at full sensor rate (6.4 kHz).
  • Automatic flight state machine and an in-flight fin-tab roll test.
  • Simulink 6DOF model, a flight-replay simulator and a flight data viewer.
  • M.I.A. adds 4 ignition channels, u-blox GPS and 915 MHz LoRa telemetry.

Project Description

Overview

Rocketry Avionics is a family of flight computers built around the Raspberry Pi RP2350B. The two boards share one core design: microcontroller, power system, sensor suite, storage and PWM outputs. ECLIPSE AFS is the flight computer for Rice ECLIPSE, and M.I.A. (Mission Independent Avionics) is my personal board. M.I.A. adds GPS, pyrotechnic ignition and telemetry so it can fly any mission on its own. Both are 4-layer boards designed in KiCad and are set up for JLCPCB assembly with LCSC part numbers.

ECLIPSE AFS

AFS is the flight computer for Rice ECLIPSE, the university's rocketry team. In the first version, team members each designed and tested one sensor circuit on its own (IMU, barometer, magnetometer, accelerometer, temperature and power sensing, plus the TPS2121 power path), then merged them into one main board. I led Version 2, a 50.8 × 87 mm 4-layer board that combines everything into one layout. It adds test points, LCSC part numbers and Gerbers ready for manufacturing.

The AFS rocket has servo-driven tabs on its four fins (PWM1–4), so the board doesn't just record the flight: it knows its own attitude and can steer roll, pitch and yaw. I wrote the AFS flight software, described below, from the sensor drivers up to navigation, flight-state logic and the tools used to analyze flights.

M.I.A. (Mission Independent Avionics)

M.I.A. starts from the same core and adds everything needed to run a flight without other electronics:

  • Pyrotechnic ignition: 4 ignition channels, each switched by an AO3400A MOSFET, with a fuse, a zener clamp and a screw terminal. A high-impedance divider on each channel senses e-match continuity before launch.
  • GPS: a u-blox MAX-M10S GNSS receiver on its own 3.3 V rail, with an SMA antenna connector.
  • Telemetry: SPI telemetry connectors for a LoRa radio module.
  • Status: WS2812B RGB LEDs and indicator LEDs.
  • Layout: first routed on 6 layers, then converted to 4 layers, with impedance-controlled traces.

Flight Software

Architecture

The AFS firmware is C++ on the Pico SDK, running FreeRTOS (V11, SMP) across both RP2350 cores. Work is split by timing: everything that has to keep up with the sensors runs on core 0, and everything that can stall runs on core 1. An SD card write can occasionally take 250 ms, so the logger lives on core 1 where it can never delay a sensor sample. The two cores talk through a fixed-size queue that never blocks the sender; if the logger falls behind, rows are counted as dropped instead of slowing navigation. Every tunable value (thresholds, hold times, rates, board geometry, task layout) lives in one config.h.

Nav task (core 0)Reads every sensor as soon as it has new data, runs the EKF, the flight state machine and the roll test, and builds a log row.
Logger task (core 1)Writes rows to flights/nav_NNN.csv on the SD card and prints a status line over serial.
Servo taskDrives the 8 PWM outputs: startup sweep, centering, holding and releasing the fin tabs.
Boot taskRuns the self-tests and startup sequence, then becomes the logger.

At power-on the board goes through a fixed sequence:

  1. Self-test: every sensor, the SD card, the RTOS and the EKF run their bench tests. The green LED turns on only if all of them pass.
  2. Servo sweep: each fin tab sweeps ±10° so the crew can see it move.
  3. Alignment (5 s): the rocket must sit still. Sensors are averaged for 0.5 s to set the starting attitude, then the EKF learns the gyro biases. The KX134 is checked against the ICM45686 here.
  4. Pad: waits for launch. The blue LED shows the rocket is within 10° of vertical.
  5. Flight: the state machine takes over (below).

Sensor Drivers and Bench Tests

I wrote a self-contained driver library for each sensor, all sharing one pattern: a constructor that stores pins and settings, begin() to reset the chip and check its ID, setters that work at any time, and reads that return an error on bus failure. Each SPI driver sets its own baud rate and mode on every transaction, so sensors with different speed limits share a bus with the SD card. The I2C drivers use 5 ms timeouts, so a missing device can't hang the bus.

Every driver has a bench test that runs at boot. It checks that the chip responds and that settings read back correctly, that readings are physically plausible (about 1 g at rest, Earth's magnetic field, room temperature and pressure), and exercises the data-ready and interrupt pins, FIFOs, and continuous and non-blocking modes. The FreeRTOS test checks core pinning, timing, cross-core queues and mutex contention (40,000 increments from both cores, none lost).

Navigation: Asynchronous Extended Kalman Filter

The core of the software is NavEKF, a 15-state error-state Kalman filter that estimates the rocket's orientation, position relative to the pad, velocity, and the accelerometer and gyro biases. It is plain C++17 with no heap allocation and no Pico SDK dependency, so the exact same code runs on the board, in the bench test and in the PC simulator.

The sensors all run at different rates (IMU 6.4 kHz, barometer ~1 kHz, magnetometer 1 kHz) and their readings don't arrive in a fixed order. Instead of resampling everything onto one clock, the filter state carries its own timestamp and each sensor is fused the moment its data arrives. A reading that shows up late is compared against what the sensor should have seen at its own timestamp (altitude h − v·lag, attitude rotated back by ω·lag).

  • Strapdown integration at full IMU rate. Position, velocity and the attitude quaternion are integrated on every 6.4 kHz sample. The 15×15 covariance is propagated every 5 ms from accumulated delta-velocity and delta-angle, which keeps the filter at about 300 flops per sample.
  • Error-state formulation. The filter estimates small errors and folds them back into the nominal state after every update, so attitude is always a proper unit quaternion with no gimbal-lock singularities.
  • Pad alignment. Gravity gives tilt and the magnetometer gives heading. While the rocket is still, zero-velocity and zero-rotation updates learn the gyro biases to about 0.003°/s.
  • Barometer corrects vertical states only. Letting it correct attitude made attitude error 6× worse in simulation, because the filter "explained" vertical errors by tilting.
  • Soft outlier gates. Outliers are fused at reduced weight (Huber-style) instead of thrown away. With hard gates, a confident filter rejected every barometer reading after burnout, ran on the IMU alone for 37 s, then jumped 200 m back in one step.
  • High-g switch. Above 15 g, the ICM45686 accelerometer (±16 g) is replaced by the KX134 until the load drops below 13 g. The gyro always comes from the ICM45686.
  • Magnetometer and transonic guards. Magnetometer readings whose field strength changes by more than 30% (motor casing, pyro currents) are de-weighted, and the barometer is locked out between Mach 0.9 and 1.1, where shock waves corrupt it.

The EKF bench test flies a simulated 45 s flight (3 s, 10 g boost to 1746 m, drogue descent) with biased, noisy, jittered sensors, rolling at 0.5 rev/s off an 85° rail:

Flight State Machine

LAUNCHPAD --launch--> POWERED_ASCENT --burnout--> CRUISING --apogee--> DESCENT --touchdown--> LANDED

The checks run on every IMU sample after alignment. States only move forward, and every condition must hold continuously for a set time, so one noisy sample can't trigger a transition. Each event also has a backup path in case the main detector misses it.

LaunchAcceleration > 3 g for 50 ms, or altitude > 30 m while climbing > 15 m/s (slow-starting motor)
BurnoutAt least 300 ms after launch, acceleration along the nose < 0.5 g for 100 ms
ApogeeAt least 1 s after burnout, EKF climb rate < 0 for 300 ms, or 10 m below peak altitude
LandedStill (|v| < 1 m/s, 1 g ± 0.2 g, < 20°/s) for 3 s, or a > 4 g impact at least 20 s after apogee

Each transition drives the hardware: at launch the EKF switches to flight noise, the fin tabs are held at center and logging jumps from 10 Hz to 300 Hz; after landing, the servos are released and logging drops back to 10 Hz. A serial state command steps through the states for bench testing.

In-Flight Roll Test

To learn how much control authority the fin tabs actually have, the software runs a system-identification experiment during the coast. All four tabs move together in doublets: +A for 0.3 s, −A for 0.3 s, then center for 0.4 s, repeating each second while A steps through 5°, 10° and 15°. The test stops when the climb rate drops below 15 m/s, after 6.5 s, or at apogee, and aborts for good if the roll rate exceeds 360°/s. Fitting roll_accel = Lδ·tab + Lp·roll_rate + L0 to each doublet gives tab effectiveness, roll damping and built-in roll bias, and plotting Lδ against dynamic pressure should give a straight line. Those numbers feed the gains of the active controller.

Logging

Each row of the navigation log has 55 columns: flight state, attitude (quaternion and roll/pitch/yaw/tilt), position and velocity, Mach and dynamic pressure, tab commands, the filter's 1σ uncertainties, its bias estimates, and diagnostics such as EKF CPU load, longest EKF step and dropped rows. Rates and accelerations are averaged over every IMU sample since the previous row, so nothing between rows is lost even at 10 Hz. An extra row is written at every state change.

Simulation and Analysis Tools

  • FinTabSim (MATLAB/Simulink): a 6DOF model of the fin-tab rocket with thrust curve, variable mass and inertia, Mach-dependent drag, per-fin aerodynamics with Barrowman normal-force slopes, servo slew limits, wind and gusts. The vehicle is read straight from the team's OpenRocket file. With tabs locked it reaches 416 m at 8.60 s against OpenRocket's 415 m at 8.60 s. With the 100 Hz roll/pitch/yaw PID controller active, tilt at apogee drops from 21° to 8°.
  • Flight replay simulator: compiles the firmware's own EKF, state machine and roll test on a PC and runs a recorded flight log back through them with different settings, in 1 ms steps. It prints the board's state changes next to the simulated ones, so a threshold or filter change can be checked against real flight data before it is flashed. A small GUI picks the log, edits settings and opens the result.
  • Flight data viewer (Python/pyqtgraph): opens SD logs with standard graphs and flight-state shading, jumps to launch, burnout, apogee or landing, and aligns several flights on any event for side-by-side comparison. It includes derived signals, A/B cursor measurements, FFT/PSD and spectrograms, zero-phase filters, ground tracks and a table comparing apogee, burn time, max speed and Mach across flights.

First Flight and What Changed

The first AFS flight in November 2026 reached about 300 m by barometer, with a 58 g landing impact recorded on the KX134. The barometer and raw sensors captured the whole flight, but the EKF's attitude drifted while the rocket waited on the pad. That corrupted its altitude and velocity estimates, and the state machine went to DESCENT 0.3 s after launch, so the roll test never ran. Running the log through the replay simulator showed the cause, and I made three fixes:

  • Pad hold with attitude: while the rocket is still on the pad, the EKF is told 100 times a second that it isn't moving and which way the nose points (the rail angle), with roll left free. The altitude zero follows weather pressure changes with a 20 s time constant.
  • Leveling after apogee: whenever the IMU is still, the averaged accelerometer direction is fed in as "up", which corrects tilt so gravity can't leak into horizontal velocity.
  • Horizontal velocity prior: once a second, a weak "horizontal velocity is about 0" update (±10 m/s under the parachute, ±1 m/s after landing) keeps position bounded without GPS.

M.I.A. Telemetry and Ground Station

M.I.A. sends telemetry over a 915 MHz LoRa link (RFM95). The flight software runs a state machine: Idle → Armed → Powered Ascent → Coasting → Descent → Recovery. On the pad, the link is two-way: the rocket sends at 1 Hz and listens for commands. Once it launches, the radio switches to transmit-only and sends packets as fast as it can. Each packet carries position, velocity, acceleration, pitch/roll/yaw, altitude, temperature and the current flight state.

A Pico-based ground station receives the packets and logs them to an SD card. A desktop app built with Dear PyGui shows the data live, along with link RSSI and SNR. It also has ARM/DISARM controls, and its LAUNCH/RESET buttons are interlocked so they only work in the correct radio mode.

Status

The ECLIPSE AFS board has flown, and its flight software now has pad hold, post-apogee leveling and the replay simulator to verify changes against real data before the next flight, where the roll test will measure fin-tab authority for the active controller. The M.I.A. PCB is finished, and its firmware is moving from Arduino to the Pico SDK so it can share the AFS drivers, EKF and RTOS layer.
